# 私域电商企微双端 Demo 集成改造清单

## 0. 总体方案与既定决策

三个关键路线已确认，后续所有条目均基于此：

| 决策项 | 结论 | 代价/约束 |
| --- | --- | --- |
| 12 项规划 HTML 如何进入双端 | 复制到 `public/plans/` 静态托管 | 文档存在两份副本，规划目录更新后需手动同步 |
| 第二个入口如何实现 | 双端内新建 `/agentic` 路由，**复用双端 `src/server`** | 只移植 UI，禁止引入第二套编排内核 |
| 本清单交付形式 | 新建 md 文档（本文件） | — |
| 多模态（语音/图片）输入 | **本轮做前置信息识别**，定位为人工效率工具 | 识别结果只做提取与提示，不获得成交阶段推进权 |
| 识别模型如何接入 | 沿用用户其他产品在用的**阿里云 DashScope**（业务空间 host + 自动补路径），新建独立配置与客户端模块 | 不改禁改的 `foundationModelConfig.ts`；无凭证时自动降级为桩实现 |
| 客户话术形态 | **分句生成，采用 B 方案**：一轮回复落库为多条消息 | `PresalesDecision.reply` 由 `string` 改 `string[]`，贯穿 5 个文件，其中 3 个原属禁改 |
| 情绪如何识别 | **不换 ASR 模型**，在多模态归一化为文本后，由既有意图识别的同一次 LLM 调用附带输出 `emotion` | 零额外调用；情绪只影响表达与客服侧优先级，不影响事实与转人工判定 |
| 成交阶段如何参与 | `dealStage` 从「事后覆写」升级为「识别输入」，同时保留 `stageGate` 事后兜底 | `orchestrateNode` 需向编排器透传 `dealState` |
| 缺失信息如何判定 | 由现状「仅 compliance 场景的 4 条正则」扩展为全场景 `missingSlots` 语义判定 | 与 `analyzeRiskContext` 并存，后者保留为合规场景的确定性兜底 |
| 限制规则承载方式 | **本轮同步外置为数据驱动**（话术约束表），`validateGeneratedReply` / `pickStyleVariant` / fallback 模板改为读取 | 改动量增大，但后续新增一类问答限制从「改 5 处代码」降为「加若干行配置」 |

核心原则四条：

1. **单一编排内核**。双端 `src/server/presalesOrchestrator.ts` 与 AgenticDemo `src/lib/presalesSkillOrchestrator.ts` 实测 diff 仅 1 行 import，已是同源双副本。`/agentic` 页面必须调用双端既有 API，不得再复制第 3 份。
2. **单一事实源在规划目录**。`私域电商售前客服-售前问答知识库.yaml`、`presales-qa-agent/scripts/answer_engine.py`、`references/agent_system_prompt.md` 由编排器跨进程读取，属于运行时依赖，不是文档。
3. **口径先统一再改代码**。当前用例条数三方不一致（实际 33 / YAML 31 / 导航索引 30），先定标准值再批量改文案。
4. **多模态只进不出**。语音/图片经前置识别转为文本与结构化字段后进入既有链路，识别结果一律标注置信度与「待人工确认」，**不得触发 `dealStage` 推进、不得进入话术作为既成事实**。这是与现有「LLM 负责理解与表达，事实由确定性规则控制」范式的一致性要求。

### 1.3 本体设计（⑩）具体修订点

同时影响 `私域电商售前客服AI规划/私域电商售前客服-业务本体设计.html`/`.yaml` 与 `私域电商售前客服AgenticDemo/docs/ontology.md`（后者是双端 `/agentic` 页面要内嵌的正本，优先改它）。

6 处待改：

1. **`ws_order_intake` 4 态扩为 7 态**。现为 `o_price_confirmed -> o_awaiting_payment -> o_screenshot_received -> o_manual_verified`，需对齐双端 `DEAL_STAGE_ORDER` 的 7 阶段，并为每一态标注**推进权归属**（AI 可推进 / 仅人工可推进）。关键事实：`nextStageFromCustomer` 仅在 `fulfillment` 工具命中时推进，且上限锁在 `awaiting_review`，其后必须 `applyManualAdvance`。
2. **新增行动边界 `ab_stage_discipline`**。现 5 条边界完全没有覆盖阶段纪律，而实现里 `enforceReplyDiscipline` + REDLINES + T02 防跳步是最强的确定性护栏。
3. **新增实体 `deal_state` 与 `agent_operator`**。前者对应 `deal_states` 表，后者对应人工客服「小禾」`U-AGENT-001`，现本体里人工只是 handoff 的接收方，没有实体。
4. **`customer_session` 状态枚举双端对齐**。AgenticDemo 本体写 `incoming|ai_serving|handoff|closed`，双端实现为 `ai_serving|human_serving|closed`。以双端实现为准。
5. **`inquiry_intent` 补 4 个维度**：`sentenceType`（question/non_question）、`subIntent`、风险维度、`hasQuestionSignal`（只升不降）。这 4 项都是实现中真实存在的分流字段。
6. **`pilot_metric` 明确口径**。`handoffRate` = 工单数/消息数、`conversionRate` = 已核对订单数/消息数，分子分母量纲不同，须显式标注为"演示口径"或改为会话级分母。
7. **新增实体 `media_asset` 与行动边界 `ab_media_extraction`**（多模态）。`media_asset` 承载语音/图片的来源、类型、识别文本、置信度、是否已人工确认；`ab_media_extraction` 的边界必须写明「只产出提取结果与提示，不产出成交事实、不推进 `dealStage`」。同时 `authenticity_proof` 与 `order_intake` 需标注其证据来源可为 `media_asset`，但确认动作仍归 `agent_operator`。

另需把 `ws_presales_reply` 从 4 步改为 6 步并插入 `stageGate`，与 `presalesGraph.ts` 的 `START → orchestrate → (humanBranch | stageGate) → END` 一致。多模态在其最前端增加一个 `s_media_normalize` 前置态：非文本消息先归一化为文本 + 结构化字段，再进入 `s_intent_routing`。

## 3. 多模态前置识别（本轮范围）

### 3.1 结论先行

**接入真实企业微信后不会自动处理，必须自建前置识别层。** 三个事实：

1. 当前双端是**模拟形态，未接入任何企业微信 API**。`src/components/Portal.tsx` 的消息收发走本地 `/api/chat`，`messages` 表的 `MessageRecord` 只有 `content: string` 一个内容字段（见 `src/types/index.ts:17`），没有类型与附件位。
2. 企业微信侧（微信客服 / 会话存档）投递的语音、图片消息给到的是**媒体标识而非文本**，需要自行下载素材再送识别，平台不提供转写与 OCR。这部分接入细节需在真正对接前查阅官方文档核实。
3. 现有链路对图片的处理是**纯话术层假动作**：`presalesOrchestrator.ts:636-637` 的 `payment_screenshot:true` 分支只是在客户说了「已付款」时回一句「已收到您的付款信息…」，**并没有真的接收或解析任何图片**。`dealStage.ts:36` 的 `payment_completed` 推进也只看意图文本。这是当前最需要补齐的地方。

### 3.2 本轮做什么 / 不做什么

本轮定位为**人工效率工具**（用户已确认）。分界线：

| 能力 | 本轮 | 说明 |
| --- | --- | --- |
| 接收语音/图片消息并落库 | ✅ | 消息类型标注 + 素材本地存储 |
| 语音转文本（ASR） | ✅ | 转写结果作为消息文本进入既有意图链路 |
| 图片信息提取（OCR / VLM） | ✅ | 付款截图提取金额、时间、单号后 4 位；商品图提取版本特征 |
| 识别结果展示在客服侧 | ✅ | 客服端 `inspector` 区展示提取字段 + 置信度 + 原图 |
| 识别结果自动推进 `dealStage` | ❌ | 明确禁止。付款核对权仍在 `applyManualAdvance` |
| 识别结果进入客户可见话术作为事实 | ❌ | 违反 REDLINES。AI 只能说「已收到，正在核对」 |
| 真实对接企业微信回调与素材下载 | ❌ | 本轮做**可插拔适配层 + 模拟投递**，真实凭证接入单列 |

**关键设计**：识别层输出统一为「文本 + 结构化字段 + 置信度 + `needsManualConfirm: true`」。编排器只消费文本部分做意图分流；结构化字段只流向客服侧 UI 与 `handoff_ticket`，不流向客户话术。这样多模态不会破坏任何一条现有护栏。

### 3.4 识别层实现

新增 `src/server/mediaPipeline.ts`，职责单一：接收素材 → 调识别 → 返回归一化结果。**不含任何业务判断，不 import `dealStage`**。

```

  normalizeVoice(assetPath): { transcript, confidence }
  normalizeImage(assetPath): { extracted, confidence, kind: "payment" | "product" | "unknown" }
```

实现方式：**在 Node 侧直接调 DashScope HTTP 接口**（详见 3.5），不引入重型 npm 依赖，也不需要 Python 侧新增脚本。原方案中的 `presales-qa-agent/scripts/media_extract.py` 取消 —— 用户已提供其他产品在用的真实接口形式，跨进程调 Python 只会多一跳。

双模式：
- **real 模式**（`DASHSCOPE_API_KEY` 非空）：走真实 DashScope 调用。
- **stub 模式**（凭证缺失或调用失败）：返回预设样例结果并把 `confidence` 置为 0、`needsManualConfirm` 置 true。保证入口二的演示链路在无凭证环境下仍可跑通，且**绝不把桩结果当作可信事实**。

置信度阈值：低于阈值时 `needsManualConfirm` 保持 true 且**不把转写文本喂给意图分类**，改为直接触发 handoff。避免错误转写引发错误话术。

#### 3.5.3 新增模块

```

src/server/dashscopeClient.ts   三个方法：chatText / recognizeImage / transcribeAudio

## 4. 话术分句生成与识别层增强（本轮范围）

### 4.1 现状问题定位（改动依据）

本节所有改动均针对已定位到具体代码行的四类问题，不做推测性重构。

**问题 1：回复啰嗦，一段话塞满所有产品信息。** 四个根因：

| # | 根因 | 代码位置 |
| --- | --- | --- |
| 1 | `validateGeneratedReply` 全是「包含式」校验，只惩罚说少、不惩罚说多。支付方式没说全（`paymentMethods.every(item => reply.includes(item))`）、价格没写进去均判不合格并回退。规则本身在推动模型往里塞更多 | `presalesOrchestrator.ts:1313-1369`，6 个 if |
| 2 | `build*FallbackReply` 本身是多字段长句拼接，且 fallback 是**高频主路径**而非异常路径 —— `getDirectReply` 命中、模型未配置、校验不过、catch 四条路都回退到它 | `:735-747`（L741 一句拼 6 个字段）、`:221-345` 四处 return |
| 3 | 工具返回 JSON 全量无裁剪注入 prompt | `:314-315` |
| 4 | 生成 prompt 的 11 条约束**全是禁止型**，无任何长度/分句/正向表达规范；`styleVariant` 只影响措辞不影响结构，且是随机抽取与客户状态无关 | `:268-280`、`:842-873` |

**问题 2：`dealStage` 是事后覆写，不是识别输入。** `orchestrateNode`（`presalesGraph.ts:61-67`）只透传 `message` + `history`，**不传 `dealState`** —— 意图识别与话术生成都不知道客户当前处于哪个成交阶段，只有 `stageGateNode`（`:75-103`）在生成完之后用 `enforceReplyDiscipline` 改写。后果是客户已付款、AI 还在介绍产品这类阶段错配。

**问题 3：链路几乎不判断缺失信息。** 唯一的判定是 `analyzeRiskContext`（`:793-827`），且：仅在 `plan.toolName === "compliance"` 时被调用（`:82`）；手段是 4 条正则匹配 4 个固定维度（既往病史/当前用药/特殊阶段/当前不适）；`knownDimensions.length >= 2` 即视为信息充足；产出只是一个字符串塞进 prompt（`:326`），**不影响工具调用、不影响转人工判定**。客户问「多少钱」未指定版本时，`buildToolArgs`（`:1181`）直接跳过 `--version`，工具取默认值返回。

**问题 4：新增一类问答限制需改 5 处硬编码，全在同一个 1370 行禁改文件内。** 这是真实的可扩展性缺陷：

1. `classifyIntentWithSkill` prompt 内的 `intent` / `toolName` / `subIntent` 枚举字符串（`:125-198`）
2. `evaluateOutcome` 的 6 分支 switch 加分支 + 新写一个 `evaluateXxxOutcome`（`:347-424`）
3. 对应的 `buildXxxFallbackReply`
4. `validateGeneratedReply` 的 if 链（`:1313-1369`）
5. `pickStyleVariant` 的 switch（`:842-873`）

叠加两重成本：这 5 处集中在同一文件；且需与 AgenticDemo `src/lib/presalesSkillOrchestrator.ts`（同源，diff 仅 1 行 import）人工双向同步，无机制保证一致。

**结论**：4 段式分层（LLM 理解 → 工具执行 → TS 判边界 → 受约束生成）方向正确，不推翻。问题在于**限制规则被硬编码为 if/switch，与项目自身「事实放 YAML、代码只做判定」的范式矛盾**。本轮同步外置为数据驱动。

### 4.3 识别层增强：IntentPlan 从 6 字段扩到 9 字段

**不新增 LLM 调用。** 情绪、缺失信息、阶段信号全部并入 `classifyIntentWithSkill`（`:125-198`，`temperature: 0.05`）的同一次调用输出。

  intent; confidence; toolName; toolArgs; subIntent; sentenceType; reasoning;
  // 新增 3 项
  emotion: "neutral" | "anxious" | "impatient" | "distrustful" | "positive";
  missingSlots: string[];         // 本轮回答缺哪些信息，如 ["version"]、["quantity"]
  stageSignal: DealStage | null;  // 从客户话里读出的阶段信号，仅作参考不直接推进
}
```

三项的用途与边界：

**（1）`emotion` —— 只影响表达，不影响事实。**

- 为什么不用 ASR 的 `emotion` 字段：① 用户现配的 `qwen-audio-3.0-asr-flash` 属 Qwen-Audio-3.0 系列，阿里云官方选型表明确标注「情感识别：不支持」；支持情感的是 `qwen3-asr-flash-filetrans`（**仅 DashScope 异步调用，需轮询 task_id**）与 `qwen3-asr-flash-realtime`（WebSocket），两者接入成本均高于当前同步单次调用；② **ASR 只覆盖语音**，客户打字发「你们这也太慢了吧」时 ASR 无输出；③ 图片 OCR 文本、语音转写文本、直接输入文本在归一化后都已是文本，可走同一判定。**故 ASR 模型不换，情绪统一在 `mediaPipeline` 归一化之后由 LLM 判文本。**
- 允许影响：`pickStyleVariant` 由**随机抽取改为按 emotion 选择**（`impatient` → 简洁告知型且句数上限降至 2；`anxious` → 风险安抚型；`distrustful` → 优先给凭据）；写入客服侧 UI 标记与工单优先级排序。
- **禁止影响**：事实字段、价格、是否转人工、`dealStage` 推进。误判情绪最坏后果只能是语气不合适，不得导致事实错误。

**（2）`missingSlots` —— 从「仅 compliance 正则」扩到全场景语义判定。**

- 与 `analyzeRiskContext`（`:793-827`）**并存**：后者保留为合规场景的确定性兜底，`missingSlots` 是全场景语义补充。两者冲突时取并集（更保守）。
- 直接用途：`missingSlots` 非空时，分句生成的最后一句即为针对缺失项的追问。这同时解决问题 1 —— 缺 `version` 时不该把 A 版 B 版全说一遍，而应问「您是想了解哪个版本」。
- 本轮**不**让 `missingSlots` 阻断工具调用（`buildToolArgs` 行为不变），避免影响既有 33 条用例通过率。

**（3）`stageSignal` + `dealState` 透传 —— 阶段从事后覆写升级为识别输入。**

- `orchestrateNode`（`presalesGraph.ts:61-67`）增加透传 `state.dealState` 给编排器。
- `classifyIntentWithSkill` 与 `generateCustomerReply` 的 prompt 均加入「当前成交阶段」，使识别与生成知道客户所处阶段。
- `stageGateNode` 的事后 `enforceReplyDiscipline` **保留**作为兜底，不因前置感知而移除 —— 双层保护。
- `stageSignal` 仅作为参考写入 trace 与客服侧提示，**不直接推进 `dealStage`**；阶段推进权仍归 `nextStageFromCustomer` 与人工操作（与原则 4「多模态只进不出」一致）。

### 4.4 限制规则外置为数据驱动

解决 4.1 问题 4。新增 `docs/reply-constraints.yaml`（双端本地文件，**不放规划目录** —— 它是双端表达层约束，非业务事实源）与读取模块 `src/server/replyConstraints.ts`。

单条约束的字段结构：

```yaml
- id: fulfillment.payment_methods
  match:
    toolName: fulfillment
    subIntent: payment_methods
  mustInclude: [payment_methods, payment_unavailable]   # 工具结果字段名，非字面量
  forbidPatterns: ["转人工", "AI", "机器人"]
  maxCharsPerSegment: 60
  maxSegments: 3
  maxFactsPerSegment: 1
  askWhenMissing: { version: "您是想了解哪个版本？" }
  styleByEmotion:
    neutral: [直接确认型, 解释原因型, 下一步引导型]
    impatient: [直接确认型]
    anxious: [解释原因型]
  fallbackTemplate:
    - "支持{payment_methods}"
    - "{payment_unavailable}暂时没开通"
```

被改造为读取该配置的三处：

| 原硬编码位置 | 改为 |
| --- | --- |
| `validateGeneratedReply` `:1313-1369` 的 6 个 if | 遍历命中的约束条目，执行 `mustInclude` / `forbidPatterns` / 三个上限 |
| `pickStyleVariant` `:842-873` 的 switch + 随机抽取 | 按 `styleByEmotion[plan.emotion]` 取候选 |
| `build*FallbackReply` 系列 | 按 `fallbackTemplate` 渲染为短句数组 |

**保持硬编码不动的部分**：`evaluateOutcome` 的 6 分支 switch 与各 `evaluateXxxOutcome`（`:347-424`）。理由：它们判定的是**行动边界与是否转人工**，属于确定性事实控制，不是表达约束，外置会削弱安全性。

外置后新增一类问答限制的成本：`reply-constraints.yaml` 加一个条目 + 视情况在 `evaluateOutcome` 加一个分支 —— 由 5 处降为 1~2 处。

`mustInclude` 采用**字段名而非字面量**是关键设计：避免配置里出现价格等硬编码数值，值仍从工具结果动态取。

### 4.5 三项话术改动的具体落点

**改动一：生成 prompt 补正向表达规范。** `generateCustomerReply` 的 system 段（`:268-280`）现有 11 条约束全为禁止型，模型只知边界不知形态，默认行为即「把工具 JSON 全部翻译成中文」。在该数组末尾追加形态约束：

```ts
"- 一次只回答客户当前问的那一个点，客户没问的信息不要主动补。",
`- 每条话术不超过 ${constraint.maxCharsPerSegment} 字；需要说多个点时拆成多条，不要用分号堆在一句里。`,
"- 先给结论，再给一句必要的解释；不要先铺垫再说结论。",
`- 最多输出 ${constraint.maxSegments} 条；结尾最多一个追问，且追问必须推进成交下一步。`,
missingSlots.length > 0 ? `- 最后一条必须追问：${askWhenMissing}` : null,
```

同时输出 JSON 契约改为 `{ customer_reply: string[] }`，由模型直接产出分句而非事后机械切分 —— 机械按标点切会切出语义不完整的碎句。

**改动二：校验补上限维度（反向约束）。** `validateGeneratedReply` 现有 6 个 if 全为「包含式」，只判「说少了」。在 4.4 的配置驱动下补三类反向判定：单条超 `maxCharsPerSegment`、条数超 `maxSegments`、单条事实字段数超 `maxFactsPerSegment`，以及跨条重复短语检测。

**顺序依赖（重要）**：改动二必须与改动三同批完成。现有不合格处理是 `return fallbackReply`，而 fallback 本身是长句 —— 若只做改动二，会出现「判定太长 → 回退到更长的 fallback」的反向效果。

**改动三：fallback 重写为短句数组。** `buildVersionFallbackReply`（`:735-747`）L741 一句拼 6 个字段、L746 一句拼 name + product_form + package_desc + 全部档位。这一项优先级不低于前两项，因为 **fallback 是高频主路径**：`getDirectReply` 命中、模型未配置、校验不过、catch 四条路都走它（`:251-258`、`:341-344`）—— 用户观察到的「一段文本塞满产品信息」很可能根本没经过 LLM。

改造形态：由「一句长拼接」改为「先答一句 + 必要补一句 + 问一句」的数组，模板见 4.4 `fallbackTemplate`。

## 7. 遗留风险（需用户决策，非本次改造范围）

1. **编排器双副本**。`presalesOrchestrator.ts` 与 `presalesSkillOrchestrator.ts` 同源 1370 行人工同步，是全项目最高漂移风险点。**v4 已放行对该文件的改造（§4），双副本必须同批同步修改**，漂移风险因此从「潜在」变为「本轮真实存在」。缓解措施：批次 F 每一步改完立刻双向 diff，验证项见 5.4 第 22 条。彻底解法（抽为共享包或单向删除一侧）仍不在本次范围。
2. **双端 8 个 API 全部无鉴权**。`senderId` 服务端硬编码，`/api/reset` 无任何保护即可清库。新增的 `/api/media/upload` 同样无鉴权且会写入网络可读的 `public/uploads/` —— **这是本轮新引入的风险敞口**，若对外演示需加最简 token 与文件类型/体积校验。
3. **`pilot_metric` 量纲问题**。分子分母不同量纲，只适合演示，不可用于真实汇报。
4. **多模态真实接入未做**。企业微信素材下载、回调验签、`media_id` 有效期、会话存档的解密与 SDK 依赖均未实现，`wecomAdapter` 只有 mock 模式。真实对接前需核实官方文档，并单独评估合规与凭证管理。
5. **DashScope 接入的待验项**（原「ASR/OCR 为桩实现」已由真实接入取代，但以下未实测）：
   - `qwen3.7-plus` 与 `qwen-audio-3.0-asr-flash` 的模型名、业务空间 host 的可用性均**未在本项目实测**，仅按用户其他产品的现用配置照录。
