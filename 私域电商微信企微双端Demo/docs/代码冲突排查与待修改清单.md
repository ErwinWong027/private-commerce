### 1.3 原本意图解决的问题

- 图片分支解决「客户在微信里发付款截图 / 产品照片，客服系统必须能读懂」。

两者都是客服系统的核心诉求，**方向都对，问题只在于合并未收尾**。

## 2. B 类：功能与客服系统既定要求不符（11 项）

### B1. 10 个 API 路由全线零鉴权，`senderId` 硬编码

- **表现**：`src/app/api/**` 下所有路由都没有身份校验，只用查询参数 `?role=customer|agent` 区分身份；`conversationService.ts:18` 写死 `U-CUSTOMER-001`、`:63` 写死 `U-AGENT-001`；`repository.ts:107-108` `getUserForRole` 同样硬编码这两个 ID。任何人改一个 URL 参数即可冒充客服。
- **背景**：Demo 起步时只需要「左客户右客服」两个固定角色演示对话，登录体系被有意省略，后续按需求陆续加了工单、阶段推进、上传等真实能力，但身份层一直没补。
- **原意图**：用最短路径让双端界面跑起来，避免为演示引入用户表与会话鉴权。
- **业务符合性**：**不符合**。不符合的具体环节是「人工接管」与「阶段推进」—— 客服系统的接管、发货标记、工单关闭都是有责任归属的动作，操作人不可伪造。Demo 阶段可接受，但必须在清单中标注为上线前阻断项。

### B2. `POST /api/reset` 无任何保护，一次清空 6 张表

- **表现**：`repository.ts:257` 的 `reset()` 直接 `DELETE` 6 张表（含 `messages`、`tickets`、`deal_states`），路由无鉴权、无二次确认、无 CSRF token，任意页面一个跨站表单即可触发。
- **背景**：为方便反复演示加的「一键重置」，当时库里只有会话与消息两张表，破坏范围小。之后工单、阶段状态、图片描述陆续入库，`reset` 的清理范围被同步扩大，风险随之放大。
- **原意图**：解决演示前需要手工删 db 文件的问题。
- **业务符合性**：**不符合**。不符合的环节是「会话与工单的持久性保证」—— 客服系统的对话记录属于可追溯凭证，不能存在无权限的全量删除入口。

### B3. `POST /api/uploads` 校验不严且阻塞事件循环

- **表现**：三个问题叠加：先 `await file.arrayBuffer()` 把整个文件读进内存**再**判断 5MB 上限（超限文件已经占满内存）；文件类型只信客户端声明的 `file.type`，而仓库里已有 `imageVision.ts:39-45` 的 `sniffMimeType` 魔数嗅探却未复用；落盘用同步 `writeFileSync`，阻塞 Node 事件循环。
- **背景**：图片多模态分支后期赶工添加，`sniffMimeType` 是给视觉模型调用写的，两处代码由同一分支的不同提交产生，没有互相复用。
- **原意图**：让客户能在 Portal 里发出图片，供后续识图链路消费。
- **业务符合性**：**部分不符合**。不符合的环节是「客户上传内容的可信性」—— 伪造 `Content-Type` 的任意文件可落进 `data/uploads`，再由 `/api/media` 原样吐出，等于给客服系统开了一个无校验的文件托管。

### B4. `GET /api/media/[name]` 无鉴权，付款截图知 URL 即可读

- **表现**：`media/[name]/route.ts:5` 的 `FILENAME_PATTERN` 已正确挡住路径穿越，但没有会话归属校验：任何人拿到文件名即可读取任意客户上传的图片。
- **背景**：与 B3 同批产生，当时只考虑「Portal 里 `<img src>` 能显示」。
- **原意图**：为已上传图片提供一个可直接放进 `img` 标签的读取地址。
- **业务符合性**：**不符合**。不符合的环节是「客户隐私数据的访问控制」—— 客服场景上传的正是付款截图、身份证明、体检单一类敏感材料，必须限定为「该会话参与方 + 已鉴权客服」才可读。

### B5. `GET /api/conversations/[id]?role=agent` 带副作用，会清未读

- **表现**：一个 GET 请求顺带执行了「清零未读数」的写操作。任何预取、爬虫、浏览器重复请求都会把未读标记抹掉。
- **背景**：前端只有一个「打开会话」动作，为省一次请求把「读详情」和「标记已读」合并在同一个 handler 里。
- **原意图**：避免前端为标记已读再发一个 POST。
- **业务符合性**：**不符合**。不符合的环节是「未读提醒的准确性」—— 客服工作台靠未读数决定响应顺序，被误清等于漏客。应拆出显式的 `POST /api/conversations/[id]/read`。

### B6. 工单缺状态机校验，接管流程可被绕过

- **表现**：`repository.ts:239-247` 的 `updateTicket` 只做字段覆盖，不校验状态迁移。由此可以：跳过「接管」直接 `resolve`；对同一工单重复「接管」，每次都刷一条系统消息；`resolve` 时无条件把会话切回 `ai_serving`，即便当前并非人工接管态。另外 `:243-244` 把 `assigned_agent_id` 硬编码为 `'U-AGENT-001'`。
- **背景**：工单表是在会话/消息之后追加的，最初只有 `open`/`resolved` 两态，`updateTicket` 作为通用 setter 写成了无约束更新；后来加入「人工接管中」态，setter 没有跟着补约束。
- **原意图**：用最少代码支持「转人工 → 处理完 → 回到 AI」这条链路。
- **业务符合性**：**不符合**。不符合的环节是「接管与交接的状态一致性」—— 这是客服系统最核心的流转逻辑，必须显式定义 `open → human_serving → resolved` 的合法迁移，非法迁移直接拒绝。

### B7. `POST /api/deal/advance` 无角色与会话状态守卫

- **表现**：阶段推进接口不校验调用方是否为客服、不校验会话是否处于人工接管态。客户侧同样能调用它把阶段推到「已发货」。`README.md:72` 声称「人工接管期间进度按钮不推进」，代码里没有对应判断。
- **背景**：`dealStage.ts` 的 `applyManualAdvance` 已实现「非法迁移原样返回」的防跳步，接口层认为状态机已经兜住，于是省掉了角色判断；README 的那句话是设计意图，实现时漏了。
- **原意图**：给客服一个「确认收款 / 已发货 / 已签收」的手动推进入口，让 AI 话术只能引用已确认的事实。
- **业务符合性**：**不符合**。不符合的环节是「成交事实的唯一可信来源」—— 阶段是话术红线的依据，写入权必须收敛到已鉴权客服，且需与 README 描述对齐。

### B8. AI 决策明细直接下发到客户端

- **表现**：会话详情接口把 AI 的 `decisions`（意图、置信度、是否静默拦截、是否建议转人工、trace）一并返回给前端，客户侧页面也能拿到。
- **背景**：为了在客服侧调试面板展示决策链路而加，客户端与客服端复用同一个详情接口，没有按角色裁剪字段。
- **原意图**：让演示者能直观看到「意图识别 → 工具执行 → 边界判定」的中间过程。
- **业务符合性**：**不符合**。不符合的环节是「静默拦截」—— 拦截之所以叫静默，就是不能让客户知道自己被拦；把 `silentIntercept` 与置信度暴露给客户端，直接破坏这个机制。应按 `role` 裁剪响应。

### B9. `unreadCount` 单向只统计客户消息

- **表现**：`repository.ts:198` 仅在 `actor === "customer"` 时给 `unread_count` +1。客服发出的消息不会在客户侧形成未读。
- **背景**：未读数最初只服务于「客服工作台的待处理列表」，客户端当时是一个始终打开的单会话页面，不需要未读。
- **原意图**：让客服侧会话列表能按待回复排序。
- **业务符合性**：**部分不符合**。不符合的环节是「双端对等的消息提醒」—— 既然定位是双端系统，未读应按「接收方视角」分别记账，否则客户端无法做角标提醒。

### B10. 视觉模型自由文本被当作事实，且不进审计

- **表现**：`imageVision.ts:72-77` 的 prompt 要求模型输出支付平台、金额、时间、品牌、规格、剂量等信息，返回的自由文本被 `conversationService.ts:22-29` 拼成 `客户发来一张图片：${imageDescription}` 直接送进决策链路；而 `presalesOrchestrator.ts:1065-1103` 构造 trace 时**没有把 `imageDescription` 写入审计**。另外 `:59` base64 内联调用无超时、`:49-97` 任何失败都静默返回 `null`。
- **背景**：图片能力是后加的，走了「最小改动」路线 —— 把图片降维成一句文本塞进既有文本链路，因此绕过了原本为文本设计的确定性校验与审计埋点。
- **原意图**：让客服系统在不重构决策链路的前提下「看懂」客户图片。
- **业务符合性**：**不符合**。不符合的环节是「事实由确定性规则控制」这一分层范式 —— 模型读出的金额、订单号属于 LLM 幻觉高发字段，不能作为事实进入话术；且既然它影响了回复，就必须进 trace 才可追溯。图片描述应只用于「意图理解」，金额/订单等事实需走确定性校验或人工确认。

### B11. 发收款码等图片资产不受 `dealState` 约束

- **表现**：`imageTriggers.ts:13-21` 的 `selectTriggeredImageAsset` 只看 `intent` 决定发报价单还是收款码，入参 `intent: string` 未收敛为 `PresalesIntent` 类型，且 pricing 优先于 payment；整个判断与 `dealState.stage` 无关。
- **背景**：发图触发是随图片分支加的，而阶段状态机在另一条分支上，两者从未在同一份代码里协同过（正是 A 类冲突的直接产物）。
- **原意图**：把「什么时候该发图」做成确定性规则，避免 LLM 自行编造图片链接。
- **业务符合性**：**不符合**。不符合的环节是「T02 防跳步」—— 在客户还处于 `consulting` 阶段就推收款码，等于跳过需求确认直接催付；发图触发必须以 `dealState.stage` 为前置条件，并把 `intent` 类型收紧。

## 3. C 类：文件存放路径 / 项目规范不符（5 项）

### C1. `presalesOrchestrator.ts:14-20` 跨项目硬编码中文兄弟目录

- **表现**：`PROJECT_ROOT = process.cwd()`，`WORKSPACE_ROOT = ..`，再往上拼 `私域电商售前客服AI规划` / `presales-qa-agent` 得到 `SKILL_PROMPT_PATH`、`ANSWER_ENGINE_PATH`、`KNOWLEDGE_BASE_PATH`。运行时依赖「工作区目录名恰好是这个中文名 + 启动 cwd 恰好是项目根」两个隐式前提。
- **背景**：技能提示词与知识库原本放在规划文档仓库里，双端 Demo 为直接复用它们，选择了跨目录读文件而不是复制或打包。
- **原意图**：避免知识库双副本不同步。
- **业务符合性**：功能上可用，但**不符合项目规范**。不符合的环节是「可部署性」—— 换机器、换目录名、用 `npm start` 从别的 cwd 启动都会读不到文件，而知识库缺失会直接让答案引擎降级。应改为环境变量指定根路径 + 启动期存在性校验。

### C2. `uploadStorage.ts:4` 上传目录相对 cwd

- **表现**：`resolveUploadDir` 取 `PRESALES_UPLOAD_DIR || cwd/data/uploads`，默认值同样依赖启动 cwd。
- **背景**：与 C1 同一写法惯性。
- **原意图**：让本地开发零配置即可上传。
- **业务符合性**：**部分不符合**，不符合的环节是「上传文件的可寻址性」—— cwd 变化会导致新上传写到别处、旧图片 404。至少应在启动期解析成绝对路径并落日志。

### C3. AgenticDemo 的测试文件放在 `src/lib` 而非 `tests/`

- **表现**：`src/lib/presalesEngine.test.ts` 与生产代码同目录，原因是 `package.json:11` 把测试命令硬编码成了这个具体路径，移动文件就会跑不起来。
- **背景**：模板自带的测试脚本指向单文件，加售前测试时顺着模板写法就地新建。
- **原意图**：最快让测试跑通。
- **业务符合性**：**不符合规范**。双端 Demo 已确立 `tests/**/*.test.ts` 的约定，两个项目应统一；测试脚本应改为 glob 而非固定路径。

### C4. AgenticDemo 的 `tests/` 目录被当成文档目录使用

- **表现**：目录名是 `tests/`，里面放的却不是可执行测试，真正的测试反而在 `src/lib`。
- **背景**：模板残留 + 售前改造时目录语义没有重整。
- **原意图**：无明确意图，属演进遗留。
- **业务符合性**：**不符合规范**，会让新人误判测试覆盖率。

### C5. 铁路模板死代码与售前代码混放在同一 `src/lib`

- **表现**：AgenticDemo 中约 2474 行旧「铁路票务」模板代码（含 model-chat 合计约 2659 行）与售前客服代码同目录共存。`ticketPricing.ts`、`CalculatorPanel.tsx` 属传递性死代码：有 import 边但上游入口不可达，`app/page.tsx:178-200` 渲染的是售前面板。`types/index.ts:1-150` 仍留着模板注释 `Rename/change this interface`。
